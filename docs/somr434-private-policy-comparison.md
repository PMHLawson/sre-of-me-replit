# Private policy comparison maintenance

This is a bounded, authenticated source-verification capability. It is disabled by default and does not change the served legacy experience, saved owner choices, activity records, or the visible Budget/SLO screens.

## Invocation and authority

Explicit server embedding may construct `createPolicyShadowService` with a genuine comparison unit, reviewed recipe registry, scoped history provider, calculation version and exact expected-difference rules. No production recipe, activation/import coverage proof or exception interpreter is supplied by default. Synthetic test providers are not production adapters.

The optional fifth `registerRoutes` argument registers an already-constructed genuine service against that server's identity. Registration is lightweight and performs no work. There is no public maintenance endpoint, automatic GET invocation, environment switch, startup job or command-line database connection. Internal operators use `invokePolicyShadowMaintenance` or `reportPolicyShadow` with an original authenticated request. An unregistered server cannot invoke the capability. The existing generic reconciliation script remains inert.

## One consistent, bounded batch

Every enabled invocation resolves and revalidates the original owner context and reconciles the legacy-to-canonical source again before evaluating or admitting a write. The comparison-only reader supports genuine legacy/shadow contexts; existing legacy mutation and import permissions are unchanged.

The owner budget lock is taken first, without admitting a mutation. One fixed NOWAIT table-lock acquisition then protects the source, settings and result evidence for the same pinned transaction and assessment time. Acquisition failure, read limits and timeouts return an honest resource-unavailable outcome after rollback; they do not trigger an automatic retry. Reconciliation failure blocks the calculators. Derived results use the existing audited writer and lazy budget admission. A later failure rolls back the entire batch.

This protocol deliberately serializes bounded maintenance and temporarily excludes other writers. It permits ordinary readers. It is not a request-path performance design: any live scheduling or broader activation requires a separate performance review and explicit adoption. Existing deadlines and read/write limits are retained.

## Evidence and classification

Canonical copies of legacy entries and genuinely native v2 entries are separate evidence sets. Custom domains and native activity without a legacy counterpart remain explicit unsupported comparisons. Missing recipes, history authority, reviewed break interpretation or compatible windows remain unavailable. Data is not trimmed to manufacture agreement.

The report compares exactly three equivalent numeric metrics: qualifying days, recorded minutes and health score. Legacy escalation and new condition/cadence/persistence/attention/trend evidence remain visible without claiming an unapproved status mapping. Legacy error budget is a retired contract, never another health percentage.

An expected difference requires exactly one reviewed, versioned rule binding the exact source, owner, domain, policy, recipe, assessment window/boundary, metric and independently specified old/new values, with a decision citation. Extra, unmatched or ambiguous differences are defects. There are no wildcard or generated approvals. Counts and an explicit verdict distinguish a completed report from a clear comparison of its declared metrics; neither is release acceptance.

Reports retain scoped record identities, fingerprints, saved-result and policy/recipe provenance, and the saved writer's actual coverage receipt. Raw notes and anomaly explanations are excluded. Oversized reports fail through the resource boundary; raw records remain available through their existing authorized history interfaces.

## Verification and release boundary

Acceptance requires typing, real synthetic-PostgreSQL reconciliation/locking/privacy tests, both actual calculators and the existing writer, the complete application suite, build, exact source identity, formal fixture cleanup and independent review. Tests cover source drift, native/custom records, historical targets, sparse cadence and recovery, subfloor practice, exemptions, DST fractions, retries and rollback.

Source acceptance does not activate this maintenance service, create missing production authority, adopt source into Preview, modify owner data, migrate a database or publish Production. Visible scoring integration and broader rollout remain separate work.
